# Changelog

## Unreleased

### Fixed
- `ZugferdConverter` negative allowances and charges (mooxphp/e-billing#101): document and line allowances and charges skip only zero amounts instead of all non-positive ones, and the document totals BT-107 / BT-108 and the line net amount BT-131 count every amount with its sign. A negative charge or allowance (for example on a corrected invoice 384 issued as a delta) is emitted with its sign (FeRD ZUGFeRD 2.5.2 ch. 7.1.6 / 7.1.11; EN 16931 has no rule against it). Positive amounts, and so 380 and 381 documents, are emitted as before.
- `ZugferdConverter` payment terms (BT-20): the invoice's `paymentTerms` are written as given and the converter no longer composes payment terms text. Before, a due date appended the German `; zahlbar ohne Abzug bis zum <date>` to the terms (or wrote it alone, starting with `; `). An invoice with a due date but no payment terms now gets only the due date (BT-9, `ram:DueDateDateTime`), which satisfies BR-CO-25; payment terms without a due date are still written.
- `ZugferdConverter` line net amount (BT-131, `ram:LineTotalAmount`) is now line total (quantity x net price) + line-level charges (BG-28) - line-level allowances (BG-27). BT-106 is the sum of BT-131; BT-107 / BT-108 cover document-level allowances and charges only. Previously line charges were added to BT-108 and missing from BT-131, which violated BR-CO-12, BR-CO-13 and BR-S-08.

### Added
- `ZugferdInvoice` contract gains `?string $projectReference` and `?string $projectName` ([#2](https://github.com/mooxphp/zugferd/issues/2)): the buyer's project reference (EN 16931 BT-11). **Breaking for custom implementations of the contract.** `ZugferdConverter` writes it with horstoeko `setDocumentProcuringProject` as `ram:ApplicableHeaderTradeAgreement/ram:SpecifiedProcuringProject` (`ram:ID` = reference, `ram:Name` = name). The CII binding requires `ram:Name`, so an empty name falls back to `Project Reference` (horstoeko's default, set explicitly). Values are trimmed; no reference (null or blank): output unchanged. Verified with KoSIT validator 1.6.3 / XRechnung 3.0.2 in the EN16931 and XRechnung profiles (without reference, with name, without name).
- `ZugferdInvoice` contract gains `array $paymentDiscounts` (`list<array{days: int, percent: float, base_amount: ?float}>`): early-payment discount tiers. **Breaking for custom implementations of the contract.** `ZugferdConverter` writes them with horstoeko `addDocumentPaymentTermXRechnung` as one XRechnung line `#SKONTO#TAGE=<days>#PROZENT=<percent, 2 decimals>#[BASISBETRAG=<amount, 2 decimals>#]` per tier into BT-20 (`ram:SpecifiedTradePaymentTerms/ram:Description`), ahead of the free-text payment terms (horstoeko's order; BR-DE-18 prescribes the line format and a line break after the last tier, not an order). `BASISBETRAG` is written only when `base_amount` is set; without it the discount applies to the amount due (BT-115). The lines are written in every profile (same BT-20 text; BR-DE-18 is checked by XRechnung only); the due date stays in BT-9. No tiers: output unchanged. Tiers without payment terms text throw `IncompleteInvoiceException` (`Missing required field: paymentTerms (BT-20) for paymentDiscounts.`), because horstoeko drops tiers and due date when the text is empty. Verified with KoSIT validator 1.6.3 / XRechnung 3.0.2 (one tier, two tiers, `TAGE=0`, `BASISBETRAG`).
- `ZugferdConverter` payment terms text: a line starting with `#` (after optional spaces or tabs) has its leading `#` characters and the following spaces or tabs removed, with or without tiers, so free text can never be read as a `#SKONTO#` line (BR-DE-18, fatal). Text that is empty after that counts as no payment terms.
- `ZugferdInvoice::$documentNotes` is now `list<DocumentNote>`, with the PHPStan type `DocumentNote` (`string|array{text: string, subject_code?: ?string}`) defined on the contract; plain strings still work, so existing implementations are unaffected. A note with `subject_code` is written as `ram:IncludedNote/ram:SubjectCode` (BT-21). `Support\NoteSubjectCodes::isValid()` checks the code against UNTDID 4451 (horstoeko `ZugferdTextSubjectCodeQualifiers`); `ZugferdConverter` throws `InvalidArgumentException` for a code outside it (KoSIT BR-CL-08).
- `ZugferdInvoice` contract gains `?string $customerTaxNumber` (the buyer's national tax number). **Breaking for custom implementations of the contract.** EN 16931 has no business term for it (BG-7 has only BT-48, the Buyer VAT identifier), so `ZugferdConverter` keeps writing the buyer VAT id as `SpecifiedTaxRegistration schemeID="VA"` (BT-48) and writes the tax number as buyer `schemeID="FC"` only when there is no VAT id. The CII/Factur-X XSD allows `SpecifiedTaxRegistration` on any `TradeParty` in every profile, including EN16931; KoSIT validator 1.6.3 and the CEN EN16931 CII schematron ignore a buyer `FC` (no rule tests it). A receiver may ignore or drop it; the PDF still shows it.
- `ZugferdInvoiceLine` contract gains `array $partialDeliveries` (`list<array{date, delivery_note, quantity}>`) and `ZugferdNoteLabels` gains `quantity(float): string` (`EnglishNoteLabels`: up to 3 decimals, no trailing zeros, `.`). **Breaking for custom implementations of either.** `ZugferdConverter`: a line with partial deliveries gets a line period (BG-26) from the earliest to the latest date (line `deliveryDate` plus partial dates); its BT-127 note lists each part as `<despatch advice label>: <note> (<date>, <quantity> <unit>)` joined by `; ` (replaces the single despatch advice fragment); the header despatch advice (BT-16) also considers partial delivery notes, so it is omitted when they differ.
- `Moox\Zugferd\Contracts\ZugferdNoteLabels` and default `Support\EnglishNoteLabels` (the previous English strings, dates unchanged): label and date-format source for BT-127 line notes (purchase order, order date, despatch advice, consignee). A line note no longer repeats an order date equal to the header order date. `ZugferdConverter` takes it as an optional constructor argument; `ZugferdServiceProvider` binds the default with `bindIf`, so a host can bind its own implementation to emit the labels in the invoice language.
- `ZugferdInvoice` gains `?string $supplierNumber` (BT-29). **Breaking for custom implementations.** `ZugferdConverter` emits `addDocumentSellerId` when non-empty (trimmed); omits when null/empty; no scheme ID.
- `ZugferdInvoice` contract gains `array $precedingInvoices` (`list<array{number, date}>`, BG-3: BT-25 number, BT-26 issue date). **Breaking for custom implementations of the contract.** `ZugferdConverter` emits one `ram:InvoiceReferencedDocument` (IssuerAssignedID + optional FormattedIssueDateTime) per entry.
- `ShipToPartyEquality`: ship-to equals buyer when case-insensitive trimmed names match and postal fingerprints match (street, `addressLine2`/street2, postal code, country). City is **not** in the fingerprint.
- `ZugferdConverter` emission (ADR 0020): omit BT-70 / BG-15 when ship-to equals buyer; keep BT-72; VAT category **K** still emits full BG-15 (buyer postal acceptable when empty) for BR-IC-12 / BR-IC-11. Promote one shared distinct line ship-to to document BG-13 when the header is empty; otherwise divergent line parties, different PO document numbers, and non-common despatch refs → BT-127 notes.
- Line contracts: `itemAttributes` / `itemClassifications` → BG-32 / BT-158; trade refs BT-13 (`purchaseOrderReference`), BT-16 (`despatchAdviceReference`, with common line DN fallback), BT-132 via `purchaseOrderLineReference`; line allowance/charges.
- `purchaseOrderDate` is unstructured only (BT-22 / line BT-127 notes) — never OrderReference IssueDate (UBL-CR-018). Header order-date notes are assembled by adapters (e.g. e-billing `InvoiceDocumentNotes`), not by the converter as IssueDate.

### Changed
- `ZugferdConverter` no longer forces Peppol BT-23 (`urn:fdc:peppol.eu:2017:poacc:billing:01:1.0`) on every profile. XRechnung 3 keeps BT-23 via horstoeko `PROFILE_XRECHNUNG_3`; EN16931 (and other profiles with null `businessprocess`) omit BT-23.
- `ZugferdInvoice` requires `vatCategoryCode`; converter emits payment means (BT-81) and VAT category (BT-118/151) from the invoice — no hardcoded `58` / `S`.
- `mergePdfWithXml()` PDF Title metadata is configurable: `config('zugferd.pdf_title_template')` (default `%3$s : %2$s %1$s`, historical horstoeko spacing) and optional per-code map `config('zugferd.pdf_title_templates')`. Optional third argument `$documentTypeCode` selects the map entry; unknown/empty codes fall back to the default template. `ZugferdConverter::resolvePdfTitleTemplate()` exposes the resolution. `PDF_TITLE_TEMPLATE` remains the package fallback constant.
- `ZugferdConverter::convert()` / `convertToFile()` require an explicit profile key; unknown keys throw. Removed `config('zugferd.profile')` / `ZUGFERD_PROFILE` (pipeline defaults belong in the host / e-billing).

### Added

- Optional `documentNotes` on `ZugferdInvoice` (`list<string>`). `ZugferdConverter` emits each entry as BT-22 via `addDocumentNote` after document information is set.
- Optional `deliveryDate` on `ZugferdInvoice` and `ZugferdInvoiceLine`. When set on the invoice, `ZugferdConverter` emits BT-72 (actual delivery date) via `setDocumentSupplyChainEvent`. When set on a line, non-EXTENDED profiles emit a line billing period with start and end equal to that date (`setDocumentPositionBillingPeriod`); EXTENDED emits line actual delivery (`setDocumentPositionSupplyChainEvent`). The `convert($invoice, $profileKey)` profile key selects the line-date carrier. The converter never derives a header invoicing period (BG-14) from delivery dates.
- Optional `shipToName` and `shipToAddress` on `ZugferdInvoice` (and lines). When a name or an address with a country is present, `ZugferdConverter` emits ShipTo (BG-13) via `setDocumentShipTo` / `setDocumentShipToAddress`, subject to the ADR 0020 omit/promote rules above. An address without a country omits the postal address call (the name may still emit). Ship-to tax registration and contact are never written.
